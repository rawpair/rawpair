/goal Deliver a real RawPair MVP for native Linux development workspaces through Orqos, without requiring Docker or Kubernetes. Users must be able to work on multiple projects, collaborate in the editor and terminal, build and run their projects, and expose applications through controlled browser URLs.

Status: implementation delivered on 2026-10-11 across RawPair and Orqos. See docs/HANDOFF.md for the implemented paths, exact setup commands, passing checks, unverified live paths and limitations. The runtime and package implementations were committed at the user's request. No push, release publication or deployment was performed during delivery.

Read docs/HANDOFF.md and docs/HOST_MVP.md in this repository, then ../orqos/AGENTS.md and ../orqos/docs/HOST_BACKEND.md. Inspect the current implementation and worktree changes before editing. This file is the canonical goal across the relevant repositories.

Scope and ownership
Implement across ~/dev/rawpair and ~/dev/orqos. RawPair owns user authentication, workspace membership, collaboration, application visibility, and the UI. Orqos owns native workspace execution, constrained host operations, filesystem access, network setup, lifecycle, and observed status. Keep ttyd and tmux for terminal delivery and persistent shared sessions. Use Linux systemd services, cgroups, separate Unix identities, and per-workspace network namespaces. Support one Linux host and trusted collaborators first; this is not a hardened service for arbitrary untrusted tenants.

Preserve the existing Docker backend and Orqos Docker/Kubernetes APIs. Rezn and the Rezn DSL are outside the implementation scope. The stacks repository remains the container image catalog; host toolchains are installed by the operator or through user-local tools. The user handles commits, pushes, merges, and hands-on local deployment.

1. Deliver a usable native workspace lifecycle
Add a backend-independent workspace interface in RawPair and an Orqos client for host workspaces. A user can access several workspaces; default to one project per workspace, with explicit membership and persistent files. Provide create/configure, start, reconnect, stop, and removal behavior in the actual UI and API. Separately confirm destructive file deletion; stopping or removing a runtime must preserve project files by default.

Run each workspace under a dedicated Unix account, separate from Phoenix, with its own home, project directory, environment, and tmux socket. Preconfigured workspace accounts are acceptable for the first version; document their provisioning and ownership. Supervise ttyd, the dedicated tmux server, and descendants with systemd. Enforce configured CPU, memory, and task limits. Browser disconnection must leave the workspace running; explicit workspace stop must stop its descendants without affecting another workspace. Recover accurate ownership and status after an Orqos or RawPair restart, without duplicate launches or adoption of unrelated host processes. A host reboot may leave workspaces stopped; reconnect and explicit start must recover them predictably.

2. Make native project work real
Use Orqos for listing, reading, and saving workspace files under the workspace identity. Enforce the configured project root with traversal- and symlink-safe operations; never give the editor an unrestricted privileged host-file API. Keep terminal and editor access consistent with filesystem permissions. Scope shared editor documents by workspace and file, authorize collaboration connections, and preserve file contents when switching files or reconnecting. A second participant can edit the same file and join the same terminal session.

Users can run ordinary Git, build, package-management, and application commands with host-installed or user-local toolchains. Support multiple concurrent projects and processes within the workspace limits. Development servers and workers can be launched from the terminal; managed production deployments, automatic language installation, and automatic database provisioning are separate work. Document how to run a development database with its own workspace data directory.

3. Deliver workspace networking and application exposure
Give each workspace its own network namespace and loopback, so separate workspaces can use the same development and database ports. Configure virtual links, addresses, routing, DNS, outbound connectivity, and cross-workspace restrictions. One physical network interface and an ordinary external router are sufficient; Orqos performs the internal networking. Keep namespace changes within the resources owned by this deployment and clean up partial starts and stopped runtimes.

Add named HTTP applications with an internal workspace port and an HTTPS preview URL. Private access requires workspace membership; deliberate public sharing is allowed only for users permitted to change that application's visibility. Public application access must never grant terminal, editor, or management access. Support HTTP and WebSockets. Restrict proxy targets to registered workspaces and applications, rather than accepting arbitrary host URLs. Handle the fact that a workspace's localhost is different from the host's: use a namespace-local forwarder or another explicit implementation that reaches localhost-only development servers.

Keep preview applications on origins separate from RawPair management and avoid exposing its session credentials to application code. Provide workable local hostname and TLS setup, including local certificate trust where needed. Public internet access uses ordinary DNS and inbound HTTPS or an optional tunnel; it does not require special router features. Generic TCP/UDP publication is deferred.

4. Enforce access and constrain privileged operations
Replace the current chosen-username entry with real authentication and workspace authorization. Cover the UI, file API, ttyd handshake, alternative terminal channels, Yjs connections, and private application previews. Reuse authorization for all access paths. Keep Phoenix unprivileged. Protect RawPair-to-Orqos control traffic and restrict privileged launch/network/file operations to validated workspace configuration and owned resources. Do not expose unauthenticated host administration, arbitrary privileged service properties, or root workspace shells.

5. Deliver setup and operational handoff
Provide a documented native setup for RawPair, Orqos, PostgreSQL, collaboration transport, ttyd/tmux, and the reverse proxy on a normal Linux systemd host. Supply the actual service/configuration assets or scripts needed to install and start it. Host mode must not need Docker, Kubernetes, image downloads, the Docker stack catalog, or Docker-dependent startup/shutdown scripts. Preserve existing container setup as a separate option. Document prerequisites, toolchain provisioning, configuration, first login, workspace account setup, project creation, application exposure, logs, restart behavior, cleanup, and known limits.

What counts as achieved
The implementation, integration, UI, configuration, and setup assets for the capabilities above are delivered and internally coherent. The intended user workflow is two independent projects running concurrently, collaborators sharing an editor and terminal, a separate controlled HTTPS URL for each project, and stopping either workspace without stopping the other. These must be actual implemented paths, not placeholders, mocked backends, undocumented manual substitutes for missing core features, or a plan for future implementation.

Testing is not a precondition of goal success. Builds, automated tests, CI, smoke checks, local deployment, and the user's hands-on acceptance are best-effort evidence, not mandatory completion gates. Do useful checks when the environment permits, fix defects discovered within the work, and report exactly what ran and what remains unverified. Do not keep the goal open solely because a compiler, privileged host, browser, certificates, external service, CI runner, or test environment is unavailable. The user expects to build, deploy locally, use the MVP, and find further problems afterward. Conversely, missing required implementation or a known defect that prevents a core workflow is unfinished work, not something to hide behind this policy.

At delivery, update docs/HANDOFF.md with the final implemented behavior, exact operator build/setup/start instructions, changed repositories, available check results, unverified paths, and concrete limitations. Keep remaining polish distinct from missing MVP functionality. Do not claim the goal achieved just because documentation or tests were added. Do not commit, push, merge, or publish.
